## 1. What the caregiver app does, in the app's terms

1. **Sign up and get approved.** The caregiver registers, verifies their email, fills in two profile steps, uploads a licence and accepts the consents. That puts them in `under_review`. An admin decides. Only `approved` caregivers can go available or accept visits.
2. **Go available.** A switch on the home screen. While on, and while the app keeps reporting a fresh location, the caregiver is offered new visits.
3. **Receive offers.** When a patient pays, the backend offers the booking to up to 8 nearby caregivers (a "wave"), then 8 more every 10 minutes, for at most 30 minutes. Each notified caregiver gets a push ("New visit request"). The first to accept wins; everyone else gets `409`.
4. **Run the visit.** Accept, then **On my way**, then enter the **4-digit visit code** the patient reads out at the door (**Start**), then **Complete**.
5. **Get paid.** The wallet shows earnings and lets the caregiver request a withdrawal. (Nothing credits the wallet yet; see section 10.)

## 2. Conventions

| Topic | What is true | Evidence |
|---|---|---|
| Error shape | FastAPI's `{"detail": ...}`. It is **not** `{"success": false, "error": ...}`. `detail` is a **string** for almost every error, a **list of objects** for `422` validation errors, and one **object** for the admin approve `409` (not a caregiver-app call). | Sections 3 to 10 |
| Auth | `Authorization: Bearer <access_token>`. A refresh token sent as a bearer is rejected with `401` `Could not validate credentials`. | 010 |
| No token | `401` `{"detail": "Not authenticated"}` | 009 |
| Wrong account type | `403` `{"detail": "Access denied. Caregiver account required."}` (a patient token on a caregiver endpoint) | 044, 082, 132 |
| Timestamps | ISO 8601 **UTC without a `Z` or offset**, for example `2026-10-06T00:03:09.513867`. Treat them as UTC. The only exception is the push payload's `scheduled_at`, which ends in `Z`. | many |
| IDs | UUID strings. | many |
| Token lifetimes | Access token 60 minutes, refresh token 7 days. **Not measured live**: these are the configured defaults (`ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_DAYS`). | config |
| Money | Mixed units; see the traps in section 12. | |

### `profile_status` state machine

| State | Meaning | What the app shows |
|---|---|---|
| `incomplete` | Onboarding not finished. | Onboarding screens. |
| `under_review` | Submitted; waiting for an admin. | "Under review". |
| `changes_requested` | Admin asked for fixes. `changes_requested.items` and `.note` say what. | The list of items to fix and a resubmit action (resubmitting consent returns the caregiver to `under_review`). |
| `rejected` | Admin rejected. `rejection_reason` says why. | The reason. Final. |
| `approved` | Can go available and accept visits. | The app. |
| `suspended` | Admin suspended. | A suspended notice; cannot go available or accept. |

Rules the app must respect:
- **Going unavailable stops new offers.** Accepted visits are unaffected, and an offer already sent stays acceptable.
- **Going available needs a location on file** (the `409` above). Send a location first.
- **Offers also need a fresh location.** Matching only considers caregivers whose last location is at most 15 minutes old (`LOCATION_FRESHNESS_MINUTES`). Toggling the switch does **not** refresh the location timestamp (verified by a test, not captured). `GET /caregiver/home` returns `location_updated_at` so the app can warn "you are not receiving offers because your location is stale".
- **A location ping only changes availability when it says so.** `is_available` on a ping is optional: omit it and the caregiver's availability is left exactly as it is (a first ping without it creates the record as **unavailable**). Send `true`/`false` only when the user actually toggled; prefer `POST /caregiver/availability`. Background-location tasks and WebSocket pings should omit it. ## 7. Offers and bookings

### Booking `status` and `dispatch_state`

`status` (the client enum gained one value, `en_route`):

| `status` | Meaning |
|---|---|
| `pending` | Paid, not yet accepted (or unpaid). |
| `accepted` | A caregiver accepted. |
| `en_route` | **New.** The caregiver pressed On my way. |
| `in_progress` | Started (visit code entered). |
| `completed` | Done. |
| `cancelled` | Cancelled (by the caregiver, by expiry or payment failure). |
| `declined` | Exists in the enum; the caregiver `decline` action does **not** set it (see below). |

`dispatch_state` (separate from `status`; now also in `BookingResponse`):

| `dispatch_state` | Meaning |
|---|---|
| `null` | Not dispatched: unpaid, or paid before dispatch existed. |
| `dispatching` | Paid and being offered in waves. |
| `matched` | A caregiver accepted. |
| `unmatched` | 30 minutes passed with no taker. Offers already sent can still be accepted. |

Transitions caregivers cause: `pending` -> `accepted` (accept) -> `en_route` (on_my_way, optional) -> `in_progress` (start, needs the code) -> `completed` (complete). `cancel` is allowed from `accepted`, `en_route` and `in_progress`. `decline` changes nothing on the booking: it only removes that caregiver's offer. Anything else is `409`.

### List and detail

| Need | Call |
|---|---|
| Offers for the home screen | `open_offers` in `GET /caregiver/home` (minimal, no patient data) |
| My visits | `GET /booking/caregiver/bookings?status=accepted` (also `en_route`, `in_progress`, `completed`, `cancelled`, `pending`) |
| Raw offers | `GET /booking/caregiver/bookings?status=new_requests` and `GET /booking/caregiver/notifications` |
| One booking | `GET /booking/booking/{id}` (only the assigned caregiver, the booking's patient or an admin) |

**An offer is not yet the caregiver's job, so it carries no patient information.** In `new_requests`, `/caregiver/notifications` and the `decline` response, a booking the caregiver is **not assigned to** comes back as an *offer view*: `patient_details` is `null`, `condition` and `special_instructions` are `null`, `patient_address` is only the area (`"<city>, <state>"`, e.g. `"Lagos, Lagos"`), and `patient_latitude`/`patient_longitude` are rounded to 2 decimals (about 1 km), enough for a distance. Once the caregiver accepts and is the assigned caregiver, the same booking returns the full details (name, phone, exact address, condition). Build the offers screen from these fields only; never expect patient identity before acceptance.

## 12. Field-nesting and unit traps

1. **Naira vs kobo.** `/caregiver/wallet`, `/wallet/transactions`, `/wallet/withdraw` and the action response's `*_kobo` fields are **kobo integers**. `/caregiver/home.wallet_balance_naira` and `GET /booking/booking/{id}` money fields (`total_amount`, `service_fee`, `platform_fee`) are **naira numbers**. The action response has naira as **strings** (`"55000.00"`).
2. **Same booking, three shapes:** the typed booking (`GET /booking/booking/{id}`, list endpoints), the raw action-response booking, and the notifications wrapper (nested `booking.patient_details` is `null`). See section 7.
3. **`visit_code`:** always present in typed bookings, `null` for everyone but the booking's patient (and only while `accepted`/`en_route`).
4. **Present-but-null:** `rejection_reason`, `changes_requested`, `location_updated_at`, `dispatch_state`, `patient_details`, `caregiver_details` are present with `null`, never absent.
5. **`caregiver_id` vs user id:** `/auth/me` returns both (`caregiver.id` and `user_id`). Booking `caregiver_id` is the **caregiver** id.
6. **Location `recorded_at`** does not move; use `location_updated_at`.
7. **Push `scheduled_at`** ends in `Z`; every other timestamp has no `Z`. All are UTC.
8. **`decline`** does not make the booking `declined`; it stays `pending`.
9. **`reason`** on decline and cancel is accepted and discarded.

## 13. State machines and polling

- **Offers.** Do not rely on push alone. While the app is open and the caregiver is available, poll `GET /caregiver/home` every **15 to 30 seconds** (one call returns offers, visits, availability and the wallet). Waves go out every 10 minutes, so offers appear in bursts; there is no faster signal.
- **Right after accept, `on_my_way`, `start`, `complete`:** use the `status` in the response, then refetch `GET /booking/booking/{id}`.
- **While a visit is active:** the booking detail is fine to poll every 15 to 30 seconds; the location goes over the WebSocket or REST ping.
- **After a `409` on accept** ("no longer available"): drop the offer and refetch home. Do not retry.
- **After a `423`:** stop sending codes until the `Retry-After` seconds pass; show the countdown.
- **Offers expire silently.** A booking nobody takes for 30 minutes becomes `unmatched`, but outstanding offers stay acceptable; a cancelled or taken booking returns `409`.

## 14. UX consequences the app must surface

1. **Going available needs a location, and a stale location means no offers.** If `is_available` is `true` but `location_updated_at` is older than about 15 minutes, show "You are not receiving offers: your location is out of date".
2. **Every location ping must send the switch value.** Omitting `is_available` means `true` and silently turns the caregiver back on (section 5).
3. **Only approved caregivers can act.** For `under_review`, `changes_requested`, `rejected`, `suspended`, disable the switch and accept; show the status screen. Offers are empty for them by design.
4. **"This job was taken by someone else"** on `409 Booking is no longer available`. **"You're not approved yet"** on the approval `403`s.
5. **Visit code lockout is real.** After 3 wrong codes the caregiver cannot start for 15 minutes, and the correct code is refused too. Tell them how many tries are left, then show the lock countdown, and tell them to ask the patient to check the code in their app rather than guess.
6. **The caregiver never sees the code.** Do not build a "show code" screen for the caregiver; the patient reads it out.
7. **Do not display fields of an unaccepted offer beyond `open_offers`** (privacy trap, section 7).
8. **Withdrawals stay `pending`.** Say "requested"; nothing pays out automatically yet.
9. **A push is a hint, not a guarantee.** Delivery was not verified, and the backend never retries or checks receipts.
10. **Cancelling is allowed from `accepted`, `en_route` and `in_progress`, and no reason is stored.** Confirm with the caregiver before sending it.
