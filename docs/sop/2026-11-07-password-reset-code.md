# SOP: Password reset by emailed 5-digit code (`POST /auth/password-recovery`, `POST /auth/reset-password`)

| | |
|---|---|
| **What shipped** | Password reset now uses a short emailed code that people can type, for both apps. The old `{token, new_password}` form still works (deprecated) so the shipped caregiver app does not break. |

## Why
The reset email carried a ~200-character JWT the caregiver had to paste, and the new patient app needs a typable code. The owner's convention is the backend's own 5-digit email verification code. Doing this safely matters because **a 5-digit code is only 100,000 possibilities**: the whole design is about making sure it cannot be guessed, replayed, enumerated or leaked. The follow-ups listed in the forgot-password SOP (bump `token_version`, no password policy on reset) are closed here.

## How
| Area | Decision |
|---|---|
| Code | Same generator as the verification code (`secrets.choice(string.digits)` x 5). Stored as `HMAC-SHA256(key derived from SECRET_KEY, "<user id>:<code>")`, hex. A bare hash of 5 digits is brute-forced instantly; with a keyed hash a database leak alone reveals nothing. Compared with `hmac.compare_digest`. Rotating `SECRET_KEY` invalidates pending codes (they expire in 15 minutes anyway). |
| Why a migration | The brief preferred none. The legacy long token (which the shipped caregiver app pastes) must keep working beside the code, and both need an expiry; sharing `password_reset_token` would mean packing two secrets into one column. Two nullable columns are cleaner and auditable. Counters live in the existing generic `admin_rate_limits` table (no more columns). |
| Wrong guesses | Counted **per exact email address, whether or not an account exists** (key `prc:<sha256(email)>`), so the answer to a guess is identical for every address and cannot reveal who is registered. After **5** wrong codes every reset for that address is `429 too_many_attempts`, even with the right code, until a new code is requested (which clears the count). Wrong, expired, malformed and no-account all count. |
| Daily budget (review finding) | Because a new request clears the per-code count, an attacker could request 3 codes an hour and try 5 guesses each (about 0.36% per account per day, sprayable). So a second counter (`prd:`) caps **20 wrong codes per 24 h across all codes** of an address; it is **not** cleared by a new request, only by a successful reset or the window ending. Past it: `429 too_many_attempts` with `Retry-After`, and **no code is mailed** while locked. |
| Exact-address keys (review finding) | The account lookup is exact (`User.email == email`), so counters are keyed on the exact string too. A lowercased key would let a request for `VICTIM@x.com` (matches nobody, mails nobody) wipe the real address's guess count. |
| Request throttle | At most **3 emails per address per hour** (window opens at the first; key `prr:`; `blocked_until` holds the window end). Further requests get the same 200, send nothing, log WARNING `throttled`. The key is the address hash, so unknown addresses are throttled identically (no signal). Does not touch the live code. |
| Concurrency | Everything for one address runs under `pg_advisory_xact_lock(hashtext('pwreset:<hash>'))`, then the user row `FOR UPDATE` (same order in recovery and reset, so no deadlock). A burst of concurrent guesses is checked and counted one at a time; a double-submit uses the code once. Stale-row purge uses `FOR UPDATE SKIP LOCKED` so concurrent requests never wait on or deadlock over each other's rows. |
| Order of checks (reset) | Password policy **first** (depends on nothing secret, so it reveals nothing, counts nothing and consumes nothing: **a weak password does not use up the code or a try**), then the 24 h budget, the 5-try lock, then the code. Same-as-current password is **not** rejected on reset (it would leak the current password to anyone holding a code). |
| One error shape | `400 {"detail": {"code": "invalid_or_expired_code", "message": ...}}` for wrong, expired, used, replaced, malformed and no-account, and for an inactive account. `weak_password` is `400`, `too_many_attempts` is `429` (not 400: it needs a different UI and may carry `Retry-After`). |
| Success | Sets the password, **bumps `token_version`** (every other session ends, exactly like change-password), clears the code, the legacy token and the counters, returns `{"message": "Password updated successfully"}` with `Cache-Control: no-store`, **no tokens**. The user signs in with the new password, which issues tokens with the new version (verified: old access/refresh tokens 401, new login 200). |
| Enumeration | Same 200 for known, unknown, inactive and throttled addresses; same 400 for unknown vs wrong code; same 429 lockout for unknown vs known (tests and live). The email is sent in a **background task** so response time does not include the mail server. A sub-millisecond difference remains (a known address also signs a JWT and writes one row): accepted, listed below. |
| Email | Subject `<project> - Your password reset code`; the code in large type; "expires in 15 minutes, works once, never share it". **No link**: the old `oaklycare://reset-password?token=` button is gone (the caregiver app's scheme is `oaklycarecaregivermobile`, so it never opened it). While `PASSWORD_RESET_LEGACY_TOKEN_ENABLED` (default true) the legacy token is printed in small type for the shipped caregiver app. |
| Legacy form | `{token, new_password}` keeps its plain-string errors (`Invalid token`, `Invalid or expired token`; a weak password is the policy sentence as a string, never an object, so the old app cannot choke on it). It now also applies the policy, bumps `token_version`, is compared in constant time, and clears the code. Single use as before. Switch it off with `PASSWORD_RESET_LEGACY_TOKEN_ENABLED=false` once that app version is retired. |
| Secrets in logs and 422s | Log lines carry the user id only (none for an unknown address). `NEVER_ECHO_FIELDS` gains `code` and `token`, and the 422 handler now also scrubs any field whose name **ends** in `password`, `token` or `code`, and any dict/list body that contains one (a model-level error echoes the whole body as `input`). |
| Other places that clear a pending code | `ChangePasswordService.change`, `AccountErasureService._wipe_user`, `UserService.reset_password` (which also now bumps `token_version`), and `PUT /auth/profile` when email or password is sent (see follow-up: that endpoint does not persist user fields today). |
| Rejected | A longer alphanumeric code (the owner chose the 5-digit convention; the limits above are what make it safe). Sending a "no account" email to unknown addresses (more mail, still a signal). Rejecting a weak password only after checking the code (an oracle for the code). Per-user (not per-address) counters (would answer differently for unknown addresses). |

## Verification
- **Tests (52 + 2 new, all pass):** whole flow; code stored only as the keyed hash; email has the code, no link or code in a URL; sessions end after reset and login works; code works once; new request replaces the old; concurrent double-submit gives one 200 and one 400 and one version bump; expiry at 15:01 (clock pinned) and still valid at 14:59; wrong code = stable 400; 7 malformed shapes; 5 wrong then 429 even with the right code; 4 wrong still leaves the right one working; new code after lockout starts over; **10 concurrent wrong guesses give exactly 5 x 400 and 5 x 429**; counters idle an hour restart; weak passwords (3 shapes) refused over and over without consuming the code or a try; weak-password answer identical for right, wrong and unknown; unknown address identical for recovery, reset and lockout, also after a lockout is lifted by a request; inactive account; hourly throttle per address, per-address isolation, window reset, unknown address throttled too (rows hashed), stale rows purged; **24 h budget** (fresh codes do not reset it, no mail while locked, `Retry-After`, window ends after 24 h) for known and unknown addresses; a good reset clears it; a case variant cannot reset the real address's count; **caplog at DEBUG over a whole flow contains none of the code, passwords or hash; no response body contains them**; 422 bodies echo none of code, password, token or `*_token` fields; legacy form works, bumps `token_version`, keeps old errors, is single use, refuses weak and expired, can be switched off; change-password kills a pending code; `UserService.reset_password` ends sessions.

## Operate / roll back
- **Deploy:** run migration `0022` (after `0021`). Needs a working SMTP (see the forgot-password SOP) and `SECRET_KEY`. Defaults need no new env. Tune with the five `PASSWORD_RESET_*` settings.
- **Support:** to unlock an address: `DELETE FROM admin_rate_limits WHERE key IN ('prc:<h>', 'prd:<h>', 'prr:<h>')` where `<h>` is the first 32 hex chars of `sha256(<exact email>)`. To kill a pending code: set the two `password_reset_code_*` columns to NULL. Grep logs for `password-recovery: throttled`, `password-reset: wrong or expired code`, `attempts exhausted` (user ids only).
- **Roll back:** revert the code (the email template, the endpoints and the long-token flow come back together), then `alembic downgrade 0021` if wanted (drops the two columns; a pending code simply stops working).

## Follow-ups
- **Apps (not in this change):** patient `apps/patient/src/services/auth.service.ts` `resetPassword({code, newPassword})` must send `{email, code, new_password}` (it currently sends the token form; it also needs the email, which the recovery screen has); the caregiver `ResetPassword.tsx` should switch from "paste the token" to a numeric 5-digit field plus email (pre-filled) and call the code form, then read `detail.code` for `invalid_or_expired_code`, `weak_password`, `too_many_attempts`. After that app version is the minimum supported: set `PASSWORD_RESET_LEGACY_TOKEN_ENABLED=false` and delete the token form, `password_reset_token` columns and `generate_password_reset_token`.
- **Per-IP / global limiter** for `/auth/reset-password` and `/auth/password-recovery` (none exists for app users). The per-address limits stop guessing at one account but not spraying one guess at many, and cannot stop an attacker burning a victim's 3 emails an hour or 5 tries (inherent to per-address limits: the victim can always request again after the window).
- **Case-insensitive account lookup** (`User.email == email` is exact everywhere, so `Ade@x.com` is not `ade@x.com`; phone keyboards capitalise). Needs a lower-case unique index first.
- **Timing:** a known address also signs a JWT and writes a row; the gap is sub-millisecond. Equalise (dummy work) or move all of it to the background task if it ever matters.
- **`PUT /auth/profile` does not persist `full_name`, `email` or `password` in tests** (response echoes the old values and the row is unchanged): `get_current_user` and the endpoint's `db` end up as different sessions. Pre-existing, found while testing the profile clearing, not fixed here. Once fixed, the code that clears a pending reset on a password or email change there takes effect; it also should bump `token_version` on a password change.
- Add `docs/fe-integration-guide-password-reset.md` to CI's `render_fe_guide --check` list (workflow files were not touched here).
- Reset does not mark the email as verified (it proves control of the address); a product call.
- Notify the user by email or push "your password was changed" (also in the change-password follow-ups).
