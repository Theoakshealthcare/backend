# SOP: caregiver's own earning, "I've arrived", short-visit threshold as policy, cancel reason stored, CI guide checks (migration 0024)

| | |
|---|---|
| **What shipped** | (a) `caregiver_earning` (naira) on the caregiver's booking views, from the booking's snapshotted earnings terms. ## Why
Owner device-pass findings (HANDOFF 1.1 item 7): the caregiver app showed no earning on Job Details (no API field); nothing fired `caregiver_arrived` (no "I've arrived" step); the 50% short-visit rule was a code constant; a free cancel of an unpaid booking dropped the family's reason; and the CI did not check four FE guides that are generated from captures.

## How
| Decision | Why / alternative rejected |
|---|---|
| **Earning = `share(service_fee_kobo, earnings_terms.visit_share_percent)`**, the same function `credit_visit` uses, read from the booking's own snapshot (`earnings.snapshot_visit_earning_kobo`). No snapshot (or a damaged one) answers `null`, never the live policy. | The number shown must equal what completion credits, and a policy edit must not change what a caregiver was shown. `terms_for` still falls back to the live policy for crediting (unchanged). Shown only on the **assigned** caregiver's views (detail, list, the booking in the notifications list when it is theirs, the action response) and only for accepted / en route / in progress / completed. Not on offers: whether to show the pay before accepting is a product call (follow-up). Naira `float`, as the other money fields of the typed views. |
| **Arrival is an `arrived` action on the existing action endpoint**, not a new route and not a new `BookingStatus`. | The caregiver app and the generated api-client already drive every step through `/caregiver/action/{id}`; a new status value would change every client enum (the comment on `en_route` already notes this). `arrived_at` is the state. |
| Guards: assigned caregiver only (the generic branch: 403 "This booking is not assigned to you"), approved caregiver (same rule as `start`/`on_my_way`: a suspended caregiver may not begin new visits), status `accepted` or `en_route` else 409, **idempotent**: a repeat keeps the first `arrived_at` and tells no one again. No time window. | `on_my_way` is time-gated because it changes the family's cancel fee; arrival changes no money, and the owner decided `start` is not time-gated either. The notice is keyed by the assignment (`issuance_key`), so a replacement caregiver arriving is announced again; WhatsApp bookings store the time but get no notice (`caregiver_arrived` is an app-only event). `arrived_at` is cleared when the booking goes to another caregiver (`dropout.clear_on_assignment`, used by accept, admin assign and admin reassign; and the drop-out reopen). |
| `arrived_at` is on the typed booking responses (the patient sees it; an offer view and any non-assigned caregiver get `null` via `redact_offer`). | The family's app can show "arrived" from state, not only from the push. |
| **Short-visit threshold in the snapshot, not read live.** `earnings_snapshot` gains `short_visit_min_percent`; `terms_for` reads it (a snapshot from before the key means **50**, not the live value); `is_short_visit(booking, min_percent)` and `credit_visit` use it; the hold reason names the booking's percent (`short_visit_hold_reason`). The `SHORT_VISIT_MIN_PERCENT = 50` constant stays as the default / old-snapshot meaning, and `SHORT_VISIT_HOLD_REASON` is its wording, so existing tests and Finance's view of 50% holds are unchanged. | The same snapshot rule as the visit share and hold hours (a caregiver is judged by the terms the booking was made under). Rejected: reading the live policy at completion (an admin edit would re-judge visits already booked). |
| **`cancel_note`**, not widening `cancel_reason`. | `cancel_reason` is a code other code switches on (`user_cancelled`, `cancelled_by_booker`...). The note is trimmed, capped at 500, blank means none, written once (a repeat cancel replays and never overwrites), for the paid and the unpaid path. It is **not returned by any booking view** and is popped in `enrich_booking_with_details` (the action endpoint returns that dict without a response model, so a stray column would otherwise reach the caregiver). **Admins do not see it yet**: free text can hold clinical detail, and showing it needs a decision about which admin permission may read it (follow-up). |
| CI: four more `render_fe_guide --check` lines. | Each pair was verified to pass before it was added, so the first CI run does not go red on old drift. |

## Verification
- **Tests** (`test_caregiver_arrived_earning.py`): the earning on detail, list, notification-list and action response, equal to the snapshot arithmetic, unaffected by a later policy edit, equal to the completion credit (fractional fee), `null` for no/damaged snapshot, for cancelled / pending bookings, for patients, admins and a caregiver who only holds an offer; arrival stamps once, keeps status, one outbox row and one feed row, works from `en_route`, refuses another / offered caregiver, patient token and no token, refuses pending / in-progress / completed / cancelled, refuses a suspended caregiver, WhatsApp stores the time but sends no app-only event, a new assignment clears it, `start` still needs the code after arriving; the threshold: default 50, a new booking carries the policy value, boundary table around 30/36/60/50/0/100, a live change never re-judges a booked visit, a hold names the snapshot's percent, an old snapshot means 50 even if the live policy differs, admin GET/PATCH with audit row and validation; cancel note: stored, trimmed, blank, 500 vs 501, a repeat never overwrites, paid path too (also on the refund note), never in a caregiver's or patient's view. `test_arrival_policy_migration.py`: follows 0023, one head, defaults, round trip, CHECK. The golden response shapes only gained `arrived_at` / `caregiver_earning` (nulls).
- **Live** (scratch database, local fake Paystack, no worker): 29 captures: a real `/create` then payment by signed webhook; offer then accept; earning on detail, list and action; arrived, repeat, one outbox row; refusals (not assigned, patient token, no token, after start, unknown action); start with the visit code; a short visit completed under the booking's own threshold (40) is held with the percent in the reason; admin policy GET / PATCH / invalid; patient view before and after arrival; a free unpaid cancel with a reason stored and not echoed.
- **Not verified**: a delivered `caregiver_arrived` push or feed row after the action (worker not run; delivery is covered by the P8 tests and capture 16 of the notifications guide); the caregiver and patient apps (no app work here); the real Paystack.
- **Fast checks and CI parity**: `poetry check --lock`, `ruff --select E9,F63,F7,F82`, `scripts.ci_smoke` (also asserts one Alembic head), all seven `render_fe_guide --check` pairs, full pytest (result in the PR text).

## Operate / roll back
`alembic upgrade head` (instant; the existing policy row gets 50). Roll back: `alembic downgrade 0023_booking_payment_link` drops the three columns (stored arrival times and cancel notes are lost); code revert removes the `arrived` action and the new fields. A booking created before this migration has no `short_visit_min_percent` in its snapshot and means 50.
