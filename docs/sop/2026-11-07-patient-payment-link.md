# SOP: "Pay now" survives an app restart: `POST /booking/{id}/payment-link`; a clear 503 when pricing is not configured

| | |
|---|---|
| **What shipped** | (1) `POST /api/v1/booking/{id}/payment-link`: the booker gets the Paystack payment link of a booking that is still unpaid, any time before its payment window closes. Same response as `/create` plus `paystack_reference` and `payment_expires_at`. **Known limit, found by the Opus review and Paystack's own error reference: Paystack refuses to initialise a reference it has already seen, so against the real Paystack this endpoint is expected to answer 503 `payment_link_unavailable` for every booking `/create` already initialised. Everything around that call (refusals, paid check, lock, no writes) is built and tested; the working fix needs a migration and is waiting for the lead (see Follow-ups).** (2) A database with no `booking_settings` row now answers `/booking/preview` and `/booking/create` with **503** `detail.code = booking_settings_not_configured` and a log line (it was a 500 `Booking settings not configured.`). |
| **Branch / commits** | `feature/fallguard-score-payment-link` (cut from `oakly/main` `470bb3a`): commits: pricing 503, payment link, review fixes, then docs and captures. Not pushed; the lead opens the PR. |
| **Migration** | None. |
| **FE guide** | [`docs/fe-integration-guide-patient-bookings.md`](../fe-integration-guide-patient-bookings.md), section "Pay now after a restart", rendered from [`docs/fe-captures/patient/`](../fe-captures/patient/) (`scripts/capture_patient_flow.py`, section 5). |

## Why
Only `/booking/create` returned `payment_url`, so a patient who closed the app between "Book" and paying had a pending booking with no way to pay it. Found by the patient-booking device walk (ledger findings 1 and 3). The second item: on a fresh database nothing is seeded into `booking_settings` (pricing is an admin decision), and the first preview answered 500, which the app shows as a crash.

## How: the payment link
| Decision | Why / alternative rejected |
|---|---|
| **One reference per booking, never rotated.** The link re-initialises the booking's own reference (`BookingService.initialise_payment`: same email, total, callback URL and metadata as `create`). | Paystack accepts a successful charge on a reference once, so two links, two taps or an old page plus a new one **cannot charge twice**. Webhook, verify-payment, the expiry sweep and refunds all find the booking by that reference and refunds charge it, so none of them had to change. Rejected: a new reference per link (needs a place to keep every reference, a webhook lookup by booking code and refunds that know which reference was paid: a larger money-path change, and it would reintroduce a double-charge window). |
| **Nothing is written** when a link is handed out. | A retry or a double tap cannot leave a second row or a second transaction. |
| `start_payment` was split: `initialise_payment` (the Paystack call, no writes) is shared; `start_payment` keeps its cancel-on-failure behaviour for `/create`. The link endpoint **never cancels** the booking on a Paystack failure. | At create time nothing was ever payable, so cancelling is right; here the person may still hold a working link and a hiccup must not destroy the booking. |
| **Paystack is asked first** whether the reference was already paid (`verify_transaction`). Paid: it is settled with the same `settle_booking_payment` the webhook and verify-payment use (dispatch starts once), and the answer is `409 booking_already_paid`. Amount mismatch: `409 payment_under_review`, booking not marked paid. Paystack unreachable: `503 payment_check_unavailable`, nothing issued. | The "paid but webhook late" case: do not offer to pay again. Not knowing is not "unpaid" (same rule as the cancel endpoint). |
| The payment **window is checked after** the paid check and is **not extended**. Rows without `payment_expires_at` use `created_at + PAYMENT_LINK_TTL_MINUTES`, like the expiry sweep. Closed: `409 payment_window_expired`. | A payment made in time still counts even if the sweep has not run; a late link would only create a refund later. Extending the window is a business decision. |
| **One request at a time per booking:** a transaction-scoped Postgres advisory lock (`pg_try_advisory_xact_lock`) held while Paystack is called. A concurrent request gets `409 payment_link_in_progress` (retry in a moment). | The row lock is not used on purpose: the webhook needs it, and holding it across two HTTP calls would stall settlement. Rejected: blocking on the lock (the second caller would then re-initialise the same reference, which gains nothing). |
| Who: the booker only (`patient_booking_cancel.is_booker`, the same rule as cancel). Refusals use the cancel endpoint's style: `detail = {"code", "message", ...}`, reusing `PatientCancelError`. | |

Error table (`detail.code`): `not_your_booking` 403, `booking_not_found` 404, `booking_already_paid` 409 (also carries `payment_status`, `refund_required`), `booking_already_cancelled` 409, `booking_not_payable` 409 (not pending, payment failed, or no reference), `payment_window_expired` 409, `payment_link_in_progress` 409, `payment_under_review` 409, `payment_check_unavailable` 503, `payment_link_unavailable` 503 (Paystack would not initialise; Paystack's wording is not shown).

## How: pricing not configured
`BookingSettingsNotConfigured` (still an `Exception` with the old message, so the WhatsApp caller's behaviour is unchanged) is raised in `calculate_booking_preview` and `insert_booking`, logs an ERROR naming the fix, and the two patient endpoints turn it into `503 {"code": "booking_settings_not_configured", "message": "Pricing is not available right now. Please try again later."}`. **Nothing is seeded.** The migrations create the table empty on purpose, and the first version is an admin act: `POST /api/v1/booking-settings/` with `pricing.write` and a reason (later versions: `PUT`). Every new environment (staging, production, a capture or test stack) needs that one call before the first preview; the log line says so. `create` also stops mapping the error to 500, so no booking row or Paystack call happens.

## Verification
- **Tests** (`test_booking_payment_link.py`, shared fake Paystack from `app/tests/fake_meta.py`): response shape equals create's plus the two fields; **nothing written**; double tap (same reference, one booking, no transaction rows); link after `create` keeps the created reference; other patient 403 with Paystack never asked; unknown 404; paid, refunded, partially refunded, cancelled, sweep-cancelled, failed-payment and no-reference bookings refused with their codes and no Paystack call; expired window refused and not extended; an old row with no expiry; the last seconds of the window work; **paid with a late webhook** is settled (dispatch once, repeat does not re-notify) and refused; paid in time but settled after the window; amount mismatch held for review; Paystack down for the paid check issues nothing; Paystack refusing to initialise leaves the booking **untouched and payable** (and the retry works); unknown reference at Paystack is not "paid"; **races with real concurrent sessions**: five simultaneous requests give one reference and no stray rows, every loser is `payment_link_in_progress`; a second request while the first is inside Paystack is told to retry and the lock is free afterwards; a payment settling while a link is requested ends paid exactly once. Pricing: preview and create on an empty `booking_settings` are 503 with the stable code and the log line, create makes no booking and no Paystack call; with pricing present both work and the link of that booking carries create's reference.
- **Neighbour tests re-run** (they touch `BookingService`, `create`, `preview`, settlement or the response shape): listed in the branch's final report.
- **Live**: 20+ captures against the running API with the fake Paystack (create, link, double tap, wrong user, caregiver, anonymous, unknown, Paystack refusing, Paystack down, paid-but-webhook-late, repeat after paid, expired window, cancelled; and the 503 on an empty database). The late webhook, the outage and the refusal are **simulated** (labelled in the captures).
- **Not verified, and expected to fail**: a *second initialise of the same reference* against the real Paystack. The shared fake accepts it (it can now be told to refuse: `FakePaystack.reject_duplicate_reference`, used by `test_real_paystack_refusing_a_repeated_reference_is_a_503`). Paystack's error reference lists "This transaction reference has already been used on this integration" for exactly this, so the endpoint will answer `503 payment_link_unavailable`, leave the booking untouched (never cancelled, never charged), and log `Paystack would not initialise a payment link: Duplicate Transaction Reference`. One check in Paystack test mode would settle it, but the fix below is needed either way if it fails.
- **Opus review** (one round, read-only, ~20 lines): 1 major (the duplicate-reference point above: the tests passed because the fake accepted repeats; the fake and a test now show it) and 4 minors, **all fixed** in the review-fix commit except one accepted: advisory lock key widened to 63 bits of the booking id; WhatsApp bookings get the WhatsApp return URL (and a test that only the booker, not the beneficiary, may pay); the race test also asserts one Paystack call per winner. Accepted: the transaction stays open across the two Paystack calls (idle in transaction for at most about 30 s). No re-review.
- **Fast checks**: `poetry check --lock`, `ruff check --select E9,F63,F7,F82 .`, `python -m scripts.ci_smoke`, all four `render_fe_guide --check` pairs. Tests run: the new files plus 896 tests across 24 neighbouring modules (admin bookings, RBAC, expiry, earnings, dispatch, KYC webhook, money, cancel, response shapes, secrets, WhatsApp booking, access) and, after the last change, the 16 modules that use the shared fake Paystack (564 tests): all pass. The full suite is CI's.

## Operate / roll back
No configuration. Roll back by reverting the commits: the route disappears and a pending booking can only be paid from the link `create` returned; the pricing error goes back to a 500. To bring up a new environment: publish the first pricing version as above. Look in the logs for `booking_settings has no row` (pricing missing) and `Paystack would not initialise a payment link` (Paystack trouble).

## Follow-ups
- **Needs the lead's decision (migration):** keep what `/create` got from Paystack. Add nullable `bookings.payment_url` (Text) and `bookings.payment_access_code`, written by `start_payment` on success; `payment-link` then returns the stored URL after the same refusals and paid check, with no second initialise (so no duplicate-reference error, no new reference, nothing for webhook or refunds to change). Old rows without a stored URL get `503 payment_link_unavailable`. Migration numbers 0021 and 0022 are taken by open PRs, so it would be 0023 or rebased. The WhatsApp channel already keeps its link in the quote payload, which is the precedent. Rejected alternative: a fresh reference per link (needs webhook matching by booking code, refunds that know which reference was paid, and re-opens a double-charge window because the old link stays payable).
- A booking the sweep cancelled keeps `booking_already_cancelled` even if Paystack says it was paid in time: that case belongs to the webhook / verify-payment (`paid_after_expiry` refund), as before.
- `create` still wraps every error, including its own `404 Patient profile not found`, into a 500 (`except Exception`); out of scope here, but the next touch of `create` should narrow it.
- A short window (30 minutes) means "Pay now" after a long break is a `payment_window_expired`: the app should send the person back to book again.
- The advisory lock holds a database connection while Paystack is called (two calls, 15 s timeout each at worst); fine at pilot volume.
