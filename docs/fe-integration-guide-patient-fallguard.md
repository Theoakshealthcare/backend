## 1. What the feature is, in the app's terms

The patient answers a fixed questionnaire (24 questions today, each with 2 to 4 choices). Each choice carries a score; the **total** is the person's fall-risk score (maximum 40 with the seeded questionnaire). The app shows the questions, sends the answers, shows the result, and lists past assessments.

**The server computes the score.** Send which choice the person picked (`question_id` and the choice's `text`); the server looks the score up from its own stored choices and adds them up. **Any `score` the app sends is ignored.** The field is still accepted (older app builds send it) and can be dropped from the app. The score you show must be the one in the response, not one computed on the phone.

## 2. Conventions

| Topic | What is true | Evidence |
|---|---|---|
| Auth | `Authorization: Bearer <access_token>` of a **patient** account. | all |
| No token | `401` `{"detail": "Not authenticated"}` | 003, 014 |
| A caregiver token | `403` `{"detail": "Access denied. Patient account required."}`: `detail` is a **string**. | 002, 013 |
| Error shape of `submit` for a refused submission | `422` `{"detail": {"code": "...", "message": "...", "question_id": "..."}}`: **an object**. `code` is stable: switch on it. `question_id` is present for the three question-related codes. | 008 to 011 |
| Malformed body | `422` with `detail` as a **list** (FastAPI's own format), e.g. `question_id` missing. Same status, different shape: check `Array.isArray(detail)`. | 012 |
| Timestamps | ISO 8601 UTC without `Z`, e.g. `2026-11-07T17:44:24.040975`. | 005 |

## 4. Submit: `POST /api/v1/fallguard/submit`

Body: `{"answers": [{"question_id": "<uuid>", "answer": "<exact option text>", "score": <ignored, optional>}]}`. Rules, all checked by the server:

- at least one answer;
- each `question_id` at most once;
- each question must be an **active** question;
- `answer` must equal the `text` of one of that question's choices (exact text, surrounding spaces ignored; `65-74` with a hyphen is **not** `65–74` with the en dash: always send back the text you received).

Answering fewer than all questions is accepted today (the total is just lower); the app should ask all of them. One bad answer rejects the **whole** submission and stores nothing.

### 4.3 Refused submissions (all `422`, nothing stored)

| `detail.code` | When | What the app does |
|---|---|---|
| `fallguard_no_answers` | empty `answers` | Do not enable "Submit" until at least one question is answered. |
| `fallguard_duplicate_question` | the same `question_id` twice | An app bug: report it. |
| `fallguard_unknown_question` | a `question_id` that does not exist or is no longer active | Reload the questions (the questionnaire changed) and let the person redo it. |
| `fallguard_invalid_option` | `answer` is not one of the choices | An app bug or a changed questionnaire: reload the questions. |

## 6. UX consequences the app must surface

1. **Show the server's `total_score`.** It can differ from a score the phone would add up (older builds, an admin editing a choice's score).
2. **Do not treat a 422 as "try again later".** Each code needs the handling in 4.3; a changed questionnaire means reloading the questions.
3. **The AI summary may be the literal text `Unable to analyze` with an empty recommendations list** (no key, or the AI call failed). Treat it as "no summary" and show the score on its own. Do not present it as advice.
4. **There is no risk band from the server.** If the app shows "low / moderate / high" it derives that from `total_score`; the thresholds must be agreed with the owner (the seeded questionnaire's maximum is 40).
5. **The seeded choice scores for three questions look reversed** (daily drowsy medication, balanced meals, never drinking alcohol: see the SOP) and are waiting for the owner. The server now uses whatever is stored, so a correction needs no app change.
6. **A double tap on Submit creates two assessments** (there is no idempotency key); disable the button while the request is in flight.
